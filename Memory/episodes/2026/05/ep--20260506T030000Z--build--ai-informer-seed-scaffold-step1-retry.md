## Reflection

Three calls worth recording: (1) The npm-registry pre-validation during planning (`npm view @openai/codex-sdk version` → 0.128.0; `npm view @openai/codex-sdk@0.128.0 dependencies` → @openai/codex 0.128.0) made the bump a one-shot rather than a guess. Confirming the SDK→bundled-CLI linkage at the registry layer before editing the engine scaffold meant we did not need to extract the optional dependency tarball or run a probe against an arbitrary version. The lesson generalizes: when bumping a dependency to fix a vendored-binary defect, verify the new version's binary linkage at the registry layer before committing to the bump. (2) The clean-delete-then-fresh-install approach to package-lock.json regeneration (rm lockfile, npm install, then rm node_modules) avoided stale transitive resolutions that an in-place `npm update` could have left behind. The engine scaffold ships without node_modules by convention; preserving that convention after the bump (delete node_modules after lockfile regen) keeps the working-tree change minimal and reviewable. (3) Patching implement_plan.md step 1 inline this episode rather than via a separate follow-up was the right call — the corrected invocation pattern was just empirically validated end-to-end, the patch is small (two phrase swaps + ep cross-reference), and a doc that lags behind execution reality drifts further with every later step. The evaluator's metacognitive observation ("after the first executed run of any new plan step, re-read that step against the actual command transcript and patch divergences inline before continuing") is generalizable but stays below promotion threshold at one occurrence.
